# Accessibility

The landing and policy pages (`web/`) and the documentation site (`site/`, served at `/docs`)
target **WCAG 2.2 Level AA**. Section 508 of the Rehabilitation Act incorporates **WCAG 2.0 Level AA**
by reference; every 2.0 AA success criterion is also a 2.2 AA criterion, except 4.1.1 Parsing, which
WCAG 2.2 removed as obsolete and which Section 508 still lists. The pages are generated by React and
Astro, which emit well-formed markup (4.1.1 is met in practice; axe's markup rules cover duplicate
ids).

The MCP tools themselves have no user interface: an AI assistant calls them.

## What is tested automatically

`pnpm test:web` (CI job "accessibility") runs Playwright with axe-core in Chromium:

| Check | Where | Criteria |
|---|---|---|
| axe rules tagged `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, plus `best-practice` | the home, privacy policy, terms and not-found pages, and every docs page, in light and dark color schemes, at 1280 and 320 CSS px | many, including 1.1.1, 1.3.1, 1.4.3, 2.4.2, 2.5.3, 4.1.2 |
| No horizontal scrolling at 320 CSS px | same pages | 1.4.10 Reflow |
| Increased line, letter, word and paragraph spacing does not clip or overflow | the landing and policy pages | 1.4.12 Text Spacing |
| One `h1`, one banner, main and contentinfo landmark, a page title | the landing and policy pages | 1.3.1, 2.4.2, 2.4.6 |
| The first Tab reaches "Skip to main content", which moves focus to the main content | the landing and policy pages | 2.4.1 Bypass Blocks |
| Copying the server URL is announced | home page | 4.1.3 |
| The policy pages read without JavaScript, then hydrate without errors | `web/e2e/prerender.spec.ts` | 1.3.1 |
| Every code block on a docs page has its own accessible name when it scrolls | `web/e2e/docs.spec.ts` | 4.1.2 |

Design tokens (`web/src/index.css`) are chosen for contrast: text at least 4.5:1 on the surfaces it
sits on, and field borders and the focus ring at least 3:1 (1.4.3, 1.4.11).

## Not covered

- The OAuth authorization page, where a person enters their provider keys, is rendered by the server
  (`renderAuthorizationPage` in `src/auth/mcp-oauth.ts`), not by `web/`, and has no browser test. It
  has labelled fields and an announced error, but it has not been checked with axe or a screen reader.
- Automated rules cover part of the criteria. Keyboard-only and screen-reader passes over the landing
  page and the docs have not been recorded.

## Manual checks

Automated tools find only part of the problems. Before a release that changes the landing page, the
policy pages, the OAuth authorization page or the docs layout, check these by hand and record the
result in the pull request:

- **Keyboard only** (2.1.1, 2.1.2, 2.4.3, 2.4.7, 2.4.11): every page can be used with Tab,
  Shift+Tab, Enter and Space; focus order follows the page; the focus indicator is always visible
  and never hidden behind other content; no keyboard trap (the docs search dialog closes with
  Escape).
- **Screen reader** (1.3.1, 2.4.6, 4.1.2, 4.1.3): VoiceOver (macOS Safari) and NVDA (Windows
  Firefox or Chrome): headings and landmarks list correctly; the OAuth authorization page announces
  each field's label and its error; "Copied" is announced.
- **Zoom** (1.4.4, 1.4.10): browser zoom to 200% and 400% at 1280 px wide: no lost content or
  function, no horizontal scrolling at 400%.
- **Accessible authentication** (3.3.8): there is no account or password. The authorization page asks
  for provider keys; its fields allow paste and password managers.
- **Target size** (2.5.8): interactive targets are at least 24 by 24 CSS px or spaced so.
- **Consistency** (3.2.3, 3.2.4, 3.2.6): the header, footer and help links are in the same place
  and order on every landing and policy page.

Last full manual pass: not yet recorded. Keyboard, reflow and text-spacing behaviour is covered by
the automated suite above; the screen-reader and browser-zoom passes are outstanding.

## Reporting a problem

Open an [issue](https://github.com/blencorp/capture-mcp-server/issues) with the page, what you
tried, your browser and assistive technology. Problems that block access are treated as bugs.
